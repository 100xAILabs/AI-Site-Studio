## Findings: Architecture & System Design

The architecture pairs FastAPI with React 19, but suffers from synchronous I/O blocking the main asynchronous event loop and in-memory process-bound state that breaks horizontal multi-worker scalability.

### As Built
- **Process Model:** Single FastAPI web application accompanied by Celery background workers using Redis broker.
- **Layering:** Route handlers directly instantiate database transactions, perform raw file system operations, and invoke third-party synchronous APIs rather than delegating to isolated service/repository layers.
- **Where Work Runs:** CPU-intensive template zip extractions, watermarking (Pillow), and framework builds run inline within web request threads instead of offloading to Celery.
- **State & Caches:** Route resolution caches (`_SITE_RESOLUTION_CACHE`), in-memory catalog stores, and preview file paths live in worker process memory and local `/tmp` directories.
- **Schema Management:** Managed via Alembic migrations, but coupled with startup checks and raw SQL alter queries.

#### F-01: Bind Razorpay verification to stored order & enforce unique gateway payment ID

**Priority:** P0 · **Closes:** S-01 · **Severity:** Critical · **Effort:** S

**Context.** In the payment verification endpoint (`POST /api/v1/payment/verify`), client-provided Razorpay parameters are validated and the associated order is marked completed. Located in `backend/app/api/v1/routes/payment.py`.

**Current code** (`backend/app/api/v1/routes/payment.py:452-485`):
```python
    # 1. Direct client-side Razorpay signature verification
    if (
        data.gateway == PaymentGateway.RAZORPAY
        and data.gateway_order_id
        and data.gateway_payment_id
        and data.gateway_signature
        and settings.RAZORPAY_KEY_SECRET
        and not data.gateway_order_id.startswith("rzp_mock_")
        and not data.gateway_payment_id.startswith("pay_mock_")
        and data.gateway_signature != "mock_signature_verified"
    ):
        msg = f"{data.gateway_order_id}|{data.gateway_payment_id}".encode("utf-8")
        generated_signature = hmac.new(
            settings.RAZORPAY_KEY_SECRET.encode("utf-8"),
            msg,
            hashlib.sha256
        ).hexdigest()

        if hmac.compare_digest(generated_signature, data.gateway_signature):
            if not payment:
                payment = Payment(
                    order_id=order.id,
                    gateway=PaymentGateway.RAZORPAY,
                    status=PaymentStatus.CAPTURED,
                    gateway_order_id=data.gateway_order_id,
                    gateway_payment_id=data.gateway_payment_id,
                    amount=order.total,
                    currency="INR",
                )
                db.add(payment)
            else:
                payment.status = PaymentStatus.CAPTURED
                payment.gateway = PaymentGateway.RAZORPAY
                payment.gateway_payment_id = data.gateway_payment_id
```

**Problem.**
1. An attacker places an order for a cheap ₹50 item and pays for it through Razorpay, obtaining valid `gateway_order_id`, `gateway_payment_id`, and `gateway_signature`.
2. The attacker creates a second order for an expensive ₹10,000 commercial template or AI token bundle, receiving a new `order.id`.
3. The attacker submits `POST /api/v1/payment/verify` referencing the expensive `order_id`, but passing the signature triple from the ₹50 order.
4. The server computes the HMAC against the client-supplied `data.gateway_order_id` rather than the stored `payment.gateway_order_id` associated with the order.
5. The signature matches, and the expensive order is marked `COMPLETED` without payment. The attacker can reuse this signature repeatedly because `gateway_payment_id` lacks a unique constraint.

**Required behaviour.**
- MUST fetch the existing `Payment` record initiated for `order.id` and compare `data.gateway_order_id` strictly with `payment.gateway_order_id`.
- MUST reject (HTTP 400) if `payment.gateway_order_id` does not match `data.gateway_order_id`.
- MUST reject (HTTP 409) if `order.status` is already `COMPLETED`.
- MUST check if `data.gateway_payment_id` has already been recorded on any existing payment in the database, rejecting replays with HTTP 409.
- MUST add a database UNIQUE constraint on `payments.gateway_payment_id` (where not null).

**Implementation.**
1. In `backend/app/api/v1/routes/payment.py` in `verify_payment`:
```python
        if not payment or not payment.gateway_order_id:
            raise HTTPException(status_code=400, detail="No initiated payment found for this order.")

        if payment.gateway_order_id != data.gateway_order_id:
            raise HTTPException(status_code=400, detail="Gateway order ID does not match initiated order payment.")

        # Check for replay of gateway_payment_id
        existing_pay = await db.execute(
            select(Payment.id).where(
                Payment.gateway_payment_id == data.gateway_payment_id,
                Payment.id != payment.id
            ).limit(1)
        )
        if existing_pay.scalar_one_or_none():
            raise HTTPException(status_code=409, detail="Payment transaction has already been processed.")

        # Compute HMAC strictly over stored payment.gateway_order_id
        msg = f"{payment.gateway_order_id}|{data.gateway_payment_id}".encode("utf-8")
        generated_signature = hmac.new(
            settings.RAZORPAY_KEY_SECRET.encode("utf-8"),
            msg,
            hashlib.sha256
        ).hexdigest()

        if not hmac.compare_digest(generated_signature, data.gateway_signature):
            raise HTTPException(status_code=400, detail="Invalid payment signature.")
```
2. Generate an Alembic migration adding a unique constraint on `payments.gateway_payment_id`:
```python
op.create_unique_constraint("uq_payments_gateway_payment_id", "payments", ["gateway_payment_id"])
```

**Also fix.**
- `backend/app/api/v1/routes/payment.py:503-512`: In mock verification branches, ensure mock signatures cannot be accepted if `settings.ENVIRONMENT == "production"`.

**Tests to add.** `backend/tests/test_payment_verify.py`:

#### F-02: Remove unauthenticated free token order activation endpoint

**Priority:** P0 · **Closes:** S-02 · **Severity:** Critical · **Effort:** XS

**Context.** `POST /api/v1/payment/activate-token-order/{order_id}` allows finalizing pending token purchase orders and crediting AI credits to users.

**Current code** (`backend/app/api/v1/routes/payment.py:1566-1596`):
```python
@router.post("/activate-token-order/{order_id}")
async def activate_token_order(
    order_id: uuid.UUID,
    db: AsyncSession = Depends(get_db),
    current_user: User = Depends(get_current_user),
):
    """
    Activate and finalize a pending token purchase order, crediting the tokens to the user.
    """
    order_res = await db.execute(select(Order).where(Order.id == order_id, Order.user_id == current_user.id))
    order = order_res.scalar_one_or_none()
    if not order:
        raise HTTPException(status_code=404, detail="Order not found")

    order.status = OrderStatus.COMPLETED
    pay_res = await db.execute(select(Payment).where(Payment.order_id == order.id))
    payment = pay_res.scalar_one_or_none()
    if payment:
        payment.status = PaymentStatus.CAPTURED

    await _fulfill_order_licenses(db, order)
    await db.commit()
```

**Problem.**
Any authenticated user can create an order for 100,000 AI tokens, receive an `order_id`, and immediately invoke `POST /activate-token-order/{order_id}`. The endpoint marks the order `COMPLETED`, updates the payment to `CAPTURED`, and credits the tokens without verifying any payment gateway receipt, webhook, or transaction proof.

**Required behaviour.**
- MUST delete the `activate_token_order` endpoint entirely, or restrict it strictly to super-admin roles with mandatory admin audit logging.
- AI token orders MUST only be finalized and fulfilled through the verified webhook or verified `POST /verify` signature flow.

**Implementation.**
1. Delete lines 1566–1602 in `backend/app/api/v1/routes/payment.py`.
2. Ensure token order fulfillment is cleanly handled in `_fulfill_order_licenses` called exclusively from verified webhook and `verify_payment` handlers.

**Also fix.**
- Check `frontend/src/` for any calls to `/activate-token-order/` and replace them with standard `/payment/verify` invocations.

**Tests to add.** `backend/tests/test_payments.py`:
